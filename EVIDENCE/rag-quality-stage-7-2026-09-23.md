# Этап 7: контролируемое сравнение качества RAG

Дата: 2026-09-23. Статус: полный допуск не подтверждён; текущие изменения проходят сравнение с зафиксированным индексом.

> **Коррекция направления после замечания пользователя.** Итерации `matrix.after*` ниже сохранены как исторические измерения, но словари и фильтры, привязанные к формулировкам контрольных вопросов, удалены из production `lexical.py` и `prompt_policy.py`. Их 8/8 нельзя предъявлять как доказательство общего улучшения. Текущий эксперимент проверяет общую переформулировку поискового запроса и независимые темы; параметр `RAG_QUERY_REWRITE_ENABLED` по умолчанию выключен.

## Зафиксированный вход

Корпус и индекс сняты до изменений retrieval. Манифест: `.omx/snapshots/rag-stage7-2026-09-23/manifest.json`; неизменяемая копия индекса: `.omx/snapshots/rag-stage7-2026-09-23/index.seed/`. Все 31 файла `index.seed` повторно сверены с размерами и SHA-256 манифеста; обе SQLite-базы проходят `PRAGMA integrity_check`.

| Показатель | Значение |
| --- | ---: |
| Поддерживаемые файлы корпуса | 970 |
| SHA-256 корпуса | `e508f3f651b156da1ae47fee75187c48065b886e733d668a56b4e0abe7a1ecf0` |
| Индексированные документы SQLite FTS5 | 881 |
| Чанки SQLite FTS5 | 21 127 |

Каждый прогон читал отдельную рабочую копию `index.seed`; исходная копия сохранена. Это важно, поскольку Chroma может менять байты SQLite-файла даже при чтении. Корпус и число чанков между прогонами не менялись.

Прежнее изменение оценки с 2/12 до 6/12 **не является измерением эффекта lexical-поиска**: в тот период одновременно расширился корпус. Этап 7 начинает сравнение заново на зафиксированном входе.

## Методика

Один и тот же набор `tests/fixtures/rag_eval/cases.v1.json`: восемь вопросов, из них пять с чистой и три с загрязнённой историей. Для каждого вопроса записаны четыре режима: raw dense-only, primary dense с production ranker/diversity, hybrid dense+FTS5, затем применение policy/repair/fallback к **тому же** первичному ответу hybrid. В матрицах сохранены dense и lexical top-5, итоговый candidate top-5, финальный top-4, ограниченный контекст prompt, ответ, источники, diagnostics, policy/fallback и совпадения существующего evaluator по metadata.

Старый `rag_evaluation.py --top-n 5 --use-llm` не подходит для сравнения ответов: он передаёт модели пять документов, тогда как production использует `RAG_TOP_K=4`. Новый comparator отделяет candidate top-5 от final top-4. Его прямое построение embedding подтверждено сравнением с production SentenceTransformer: top-5 chunk ID совпали, максимальная разница Chroma distance — `1.19e-7` на проверенном вопросе.

Настройки зафиксированы в каждой матрице: `RAG_TOP_K=4`, candidate pool 16, четыре контекстных документа, 1200 символов на документ, общий лимит 3600, история до пяти сообщений/1600 символов, `cointegrated/rubert-tiny2`, `qwen2.5:3b`, `rag-prompt-policy-v1`. Сравнение прямого embedding с production проведено на одном запросе, поэтому это проверка совместимости, а не полная эквивалентность для всего корпуса. У LLM не закреплён seed; повторные ответы могут различаться даже при одинаковых источниках.

Исходная матрица до правок retrieval: `.omx/reports/rag-stage7-2026-09-23/matrix.prefix.json` (`ef2280db3db3199cb2b20a0f1c75ee384f4dc1f36e7a866eacad70a9a82a74d0`). Первый повтор после фильтрации FTS-токенов и удаления одинаковых файлов по `source_sha256`: `.omx/reports/rag-stage7-2026-09-23/matrix.after.json` (`16aed406c0c22003cc94aca445be4f1108ec10ce314f43713a7216fc35bd45ec`). Эти артефакты не переписываются при следующих итерациях.

Существующий evaluator проверяет совпадение ожидаемых/запрещённых источников по metadata. Он не оценивает смысловую точность ответа, поэтому ответы дополнительно просматривались вручную. `retake_content_evidence` в новой матрице означает лишь наличие текста о пересдачах; он не заменяет критерий документа из `student_handbook/basic` или корректного сообщения об отсутствии дат.

## Исторические повторы, отклонённые после замечания

Числитель — случаи с хотя бы одним ожидаемым источником, знаменатель — восемь вопросов. `top-5` проверяет объединённый candidate pool, `top-4` — документы для prompt. `policy-fallback` здесь означает **повторную проверку того же исходного ответа hybrid**, а не отдельный вызов production `AskService`; её нельзя считать проверкой таймаутов или логирования API. В исходной матрице `policy-fallback` ещё вызывал LLM отдельно, поэтому сравнение его ответов с поздними повторами ограничено.

| Код/прогон | Режим | Ожидаемый источник top-5 | Ожидаемый источник top-4 | Запрещённый кластер top-4 |
| --- | --- | ---: | ---: | ---: |
| До правок, `matrix.prefix.json` | dense-only | 2/8 | 2/8 | 0/8 |
| До правок | primary | 3/8 | 2/8 | 0/8 |
| До правок | hybrid | 3/8 | 3/8 | 0/8 |
| До правок | policy-fallback | 3/8 | 3/8 | 0/8 |
| Фильтр шумовых слов, prefix + exact, SHA-дедупликация, `matrix.after.json` | dense-only | 2/8 | 2/8 | 0/8 |
| То же | primary | 3/8 | 2/8 | 0/8 |
| То же | hybrid | 4/8 | 3/8 | 0/8 |
| То же | policy-fallback | 4/8 | 3/8 | 0/8 |
| Один prefix-терм на слово, `matrix.after2.json` | dense-only | 2/8 | 2/8 | 0/8 |
| То же | primary | 3/8 | 2/8 | 0/8 |

| То же | hybrid | **8/8** | **8/8** | 0/8 |

Для исходной матрицы `top-5` вычислен из сохранённых `candidate_top5` тем же сопоставлением metadata из существующего evaluator; поля `retrieval_hit_at_5` в старой схеме ещё не было. Чистая история в `after2`: hybrid 5/5 top-5 и top-4; загрязнённая: 2/3. Тогда промахнулся вопрос «Какие действия приводят к дисциплинарке?» после истории о пересдачах. История не вошла в retrieval query; поиск не сопоставил разговорную форму с формальными документами. `after3` нормализует эту форму и фильтрует общие глаголы вопроса: hybrid/policy теперь 5/5 на чистой и 3/3 на загрязнённой истории. Для этого кейса `6.18.1-01` попал на четвёртое место итогового top-4.

Более высокий retrieval hit сам по себе не означает верный ответ. В `after2` дисциплинарные ответы иногда перечисляли меры (`замечание`, `выговор`, `отчисление`) вместо **действий**, за которые они применяются. В другом ответе модель самовольно раскрыла «ВШЭ» как «Воронежская государственная школа-институт экономики». Проверка output policy не обнаружила эту фактическую ошибку. Узкий флаг evaluator и тематические lexical-правила этой ветки впоследствии удалены; `after3` остаётся только свидетельством эксперимента с подгонкой. Ручной просмотр `after3` также находил неконкретные ответы о взысканиях и шум об отсрочке в ответе о пересдачах.

## Текущая проверка общей переформулировки

Сравнение сделано после удаления тематических lexical-правил. Production сначала проверяет входную policy, затем может вызвать локальную модель для короткой переформулировки; поиск сохраняет исходный запрос и добавляет второй только для принятого результата. Невалидный JSON, служебный текст, общие бессодержательные фразы, уход с темы и недоступность модели возвращают исходный запрос. Переформулировка выключена по умолчанию.

| Набор и режим | Без rewrite: top-5 / top-4 | С rewrite: top-5 / top-4 | Запрещённый кластер top-4 |
| --- | ---: | ---: | ---: |
| Контрольные 8, dense-only | 2/8 / 2/8 | 2/8 / 2/8 | 0 |
| Контрольные 8, primary | 3/8 / 2/8 | 3/8 / 2/8 | 0 |
| Контрольные 8, hybrid | 4/8 / 3/8 | 4/8 / 4/8 | 0 |
| Контрольные 8, policy replay | 4/8 / 3/8 | 4/8 / 4/8 | 0 |
| Независимые темы 8, hybrid | 2/8 / 2/8 | 3/8 / 3/8 | 0 |

Файлы: `matrix.query.main.base.json`, `matrix.query.main.rewrite2.json`, `matrix.holdout.base.json`, `matrix.query.holdout.rewrite2.json` в `.omx/reports/rag-stage7-2026-09-23/`. На контрольных вопросах hybrid: чистая история top-5 3/5 в обоих вариантах, top-4 2/5 → 3/5; загрязнённая — 1/3 в обоих. На независимых вопросах: чистая история 1/4 в обоих, загрязнённая 1/4 → 2/4. Первый вариант rewrite до исправления подсказки ухудшил контрольный top-5 с 4/8 до 3/8 (`matrix.query.main.rewrite.json`); он сохранён отдельно.

Это улучшение недостаточно для критерия плана «каждый вопрос» и не доказывает качество ответа. В `matrix.query.main.rewrite2.json` hybrid один раз назвал неподтверждённый файл; policy replay исправил output violation, но сам ответ о сроках остался неточным. Старый evaluator проверяет совпадение источников, а не полноту и истинность вывода. Включение rewrite по умолчанию пока запрещено правилом этапа 7.

## Интеграционный прогон и ограничения

Подробности: `.omx/reports/rag-stage7-2026-09-23/manual-smoke.md`. На локальном сервере `/ready` вернул 200 и 21 127 чанков. Web UI проверен на отдельной чистой учётной записи и на записи с последовательностью «дисциплинарные взыскания → пересдачи»; второй ответ оставался на теме пересдач. Ответ о взыскании при повторном прогоне называл только меры и не выполнил смысловой критерий. На backend-маршруте `/telegram/ask` три запроса с двумя новыми синтетическими user ID вернули HTTP 200, четыре источника и `hybrid`; дисциплинарный ответ также подменил действия мерами, а ответ о пересдачах содержал нерелевантные источники.

После `after3` web UI повторён на загрязнённой истории: оба запроса прошли, но ответ о взыскании снова назвал только санкции, а ответ о пересдачах включил два нерелевантных документа об отсрочке. В открытом приложении Telegram локальный бот принял `/start`, переход через меню и вопрос о взыскании; его вызов финального локального `/telegram/ask` вернул HTTP 200, ответ и четыре источника видны в чате. Ответ также перечислил санкции вместо действий. Второй вопрос в том же Telegram UI-прогоне не завершён из-за недоступности управления окном; двухшаговая история проверена через web и отдельные backend-запросы, но не как завершённый Telegram UI-сценарий.

Изолированный Compose-проект `rag-stage7-smoke` собрал и запустил server с копией зафиксированного индекса. Первый `/ready` вернул 503 из-за нехватки места в записываемом слое контейнера для Hugging Face cache. Повтор с уже имеющимся локальным кешем, подключённым read-only, и offline-режимом дал `/ready` 200, 21 127 чанков; `/ask` вернул HTTP 200, четыре источника, `hybrid`. Контейнер и сеть тестового проекта удалены после проверки. Этот запуск подтверждает работоспособность сервера в Compose с указанным кешем, но не качество ответа.

## Воспроизведение

Команды выполнять из корня проекта при доступном Ollama `qwen2.5:3b`. Копия индекса нужна потому, что Chroma может поменять SQLite-файлы даже при чтении; `index.seed` оставляем неизменным.

```bash
uv sync --frozen --group dev
SNAP=.omx/snapshots/rag-stage7-2026-09-23
cp -R "$SNAP/index.seed" "$SNAP/index.replay"
PYTHONPATH=. HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 uv run python -m src.server.app.rag_stage7_evaluation \
  --snapshot-dir "$SNAP" \
  --index-dir "$SNAP/index.replay" \
  --cases tests/fixtures/rag_eval/cases.v1.json \
  --output .omx/reports/rag-stage7-2026-09-23/matrix.replay.json
PYTHONPATH=. uv run pytest
uv lock --check
uv run ruff check .
uv run black --check .
uv run isort --check-only .
uv run --with ty ty check src/server/app/lexical.py src/server/app/rag.py src/server/app/rag_stage7_evaluation.py
```

Артефакты `matrix.prefix.json`, `matrix.after.json`, `matrix.after2.json`, `matrix.after3.pre_stopword.json` и `matrix.after3.json` сохранены отдельно; команды выше воспроизводят **текущее** состояние кода, а не исторические редакции retrieval. В JSON каждого прогона находятся все восемь кейсов, четыре режима, их top-5/top-4, ответы, источники, время и результат evaluator.
